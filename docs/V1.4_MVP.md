# 6. 最重要的架构决策

## 6.1 不让 Agent 主动读取 IndexedDB

最终决定：

> **Coze Agent 不主动读取 IndexedDB。**

原因：

1. IndexedDB 存在用户浏览器；
2. Coze Agent 运行在远程服务器；
3. Agent 无法直接访问浏览器本地数据库；
4. 强行设计 Tool Bridge 会显著增加开发复杂度；
5. 当前没有必要为厨房问答增加双向工具调用架构。

---

## 6.2 使用 Context Injection

采用：

> **Context Injection（上下文注入）**

即：

```text
IndexedDB
↓
本地 App 读取
↓
结构化 AgentContext
↓
/api/chat
↓
Coze Agent
```

# 11. 为什么每轮重新读取 IndexedDB

`session_id` 与 IndexedDB 的职责不同。

```text
session_id
=
我们之前聊了什么

IndexedDB
=
用户现在真实有什么
```

例如：

```text
第一轮：
鸡蛋 × 6

用户随后在库存中：
标记鸡蛋已用完

第二轮继续聊天
```

第二轮 Agent 必须看到：

```text
当前库存中已没有鸡蛋
```

因此每轮发送前必须重新调用：

```text
buildAgentContext()
```

# 14. Context Builder

服务端根据结构化 Context 生成文本：

```text
【家庭食材助手当前实时上下文】

当前库存：
- 番茄：2个（临期）
- 鸡蛋：6个（新鲜）

过敏：
- 花生

忌口：
- 香菜

【重要规则】
以上信息来自用户本轮发送消息时的本地实时数据。
如果这些信息与历史聊天中的旧库存冲突，以本轮数据为准。

【用户问题】
今晚吃什么？
```

# 15. Coze Agent 端需要做什么

Agent 已经完成主要能力。

本次只需要确认 Agent 系统规则包含：

```text
1. App 可能会注入当前库存、过敏、忌口。
2. 本轮注入数据是当前实时事实。
3. 与历史库存冲突时，以本轮数据为准。
4. 不得声称自己可以直接读取 IndexedDB。
5. 不得自行假设用户拥有未提供的食材。
6. 过敏食材必须严格排除。
7. 忌口食材不得主动推荐。
8. 如果用户问题和库存无关，不需要强行引用库存。
```

这属于一次性接口适配说明，不代表 App 需要维护 Agent Prompt。
